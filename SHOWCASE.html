Decision Logic

Why every intent gets a different retrieval path

The router is where most of the actual engineering lives. A flat vector search over everything would work — badly. This table is the difference between "technically works" and "production correct."

IntentExampleRouteWhy this and not vector-only
branch_info"Where is Al Karama?"SQLAddress is a fact in a row, not a paragraph to rank
doctor_search"ENT doctor at Qusais?"SQL → Vector fallbackJOIN on branch+speciality beats semantic similarity every time
insurance_check"NAS covered at JVC?"SQLExact lookup — no ambiguity for a vector to "interpret"
speciality_info"What does physio treat?"SQL + VectorNeeds both the branch list (fact) and the description (prose)
general_health"Symptoms of diabetes?"Vector + BM25 → RRFGenuinely open-ended; needs semantic recall + keyword precision
emergency"Chest pain right now"Hardcoded ruleZero LLM calls — safety paths never depend on classification succeeding
Tech Stack

No framework hiding the logic

Every retriever, every fusion algorithm, every intent classifier is hand-written. The libraries below are infrastructure — not the intelligence.

Scraping
Firecrawl
Only option that renders Elementor's client-side JS before extracting markdown
Structured store
SQLite
12 tables, FK joins, zero ops — migrates cleanly to Postgres if scale demands it
Vector store
ChromaDB
Metadata filtering built in — scope before rank, not after
Embeddings
all-MiniLM-L6-v2
Served via onnxruntime — 5× lighter than torch for the same vectors
Keyword search
BM25Okapi
Catches exact-match recall that semantic similarity misses
Fusion
RRF (k=60)
Score-free way to combine two differently-scaled rankings
LLM
Claude Sonnet 4.6
Intent classification AND grounded final response generation
Deploy
Docker + Render
render.yaml blueprint — one-click reproducible deploy
